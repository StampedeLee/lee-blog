# FAST API 中间件

中间件（Middleware）可以理解为：

在请求进入后端业务逻辑之前，或者响应返回前，统一经过的一层处理模块

1. CORS 跨域中间件

CORS（Cross-Origin Resource Sharing，跨域资源共享）用于解决前后端不同域名之间无法通信的问题。

作用：

允许指定域名访问后端 API；
控制允许的方法（GET、POST等）；
控制允许携带的请求信息。

2. JWT 认证中间件

JWT（JSON Web Token）用于用户身份认证和权限控制。

FastAPI 路由分发（Router Dispatch）

在经过 FastAPI 入口以及基础中间件之后，下一步核心模块是：

# 路由分发（Routing）

路由分发的作用：

根据用户请求的不同 URL 或操作，将请求转交给对应的后端处理逻辑。

#### 文件处理
doc的处理非常方便，都有相应的标签

PDF 解析过程较为复杂，通常需要经过多个模块协同处理。
可能会依次调用 image、layout、table Transformer、text merge、extract table figure、content download 等多个函数

##### image
##### 1. PDF 页面处理

首先将 PDF 每一页转换为图片，方便后续进行 OCR 识别。

同时通过 PDF 解析工具（如 pyPDF2 等）获取 PDF 原始结构信息，例如页面层级、文本层等。


##### 2. 语言检测与字符解析

解析前需要判断页面主要语言类型。

通常通过随机抽取部分字符进行语言检测：

- 英文文本通常以单词作为基本单位，每个单词对应一个坐标；
- 中文文本通常以单个字符作为基本单位，每个文字对应一个坐标。

针对中英文混合文档，使用字符级解析器处理不同语言的文本单位，保留字符级别的位置关系，方便后续布局恢复。


##### 3. OCR 解析

对于 PDF 中无法直接获取文本的信息（例如扫描件、图片文字），使用 OCR 进行文字识别。

OCR 输出：

- 文本内容；
- 内容类型（文字、表格、图片等）；
- 位置坐标（boxes）。


##### 4. Boxes 坐标信息

`boxes` 用于记录每个内容块在 PDF 页面中的位置。

作用：

- 确定文本、图片、表格等元素的位置关系；
- 根据空间关系恢复原始页面布局；
- 辅助后续文本合并和 Chunk 切分，保证语义完整性。

##### layout
OCR 解析（此处获得类别信息）后可以得到 PDF 页面中的文本内容、内容类型以及坐标信息，但还需要进一步判断每个内容块在文档中的具体角色。

Layout 模块负责对 OCR 得到的每个区域进行分类和布局分析，判断该内容属于哪一种文档元素
- 标题（Title）
- 正文（Text）
- 图片（Image）
- 表格（Table）
- 图片说明（Figure Caption）
- 表格说明（Table Caption）
- 页眉（Header）
- 页脚（Footer）
- 参考文献（Reference）
- 公式（Formula）

##### tabletransfomer job
Table Transformer Job 主要用于 PDF 中表格内容的识别和结构恢复。
对于表格区域，**第一阶段** OCR 可能只能获取基础信息，但无法很好地恢复复杂的表格结构。因此需要进一步进行表格增强处理。
Table Transformer 通过模型识别表格区域，并恢复：

- 表格边界；
- 行列结构；
- 单元格关系。

##### textmerge
Text Merge 负责将 OCR 解析得到的离散文本块重新组合成符合阅读逻辑的完整文本。

OCR 通常是逐行或逐块识别文本，但无法理解这些文本之间的语义关系，Text Merge 会结合 OCR 提供的文本内容、boxes 坐标以及 Layout 分类结果，判断文本块之间的位置关系和结构关系。

##### extract table figure
Extract Table Figure 负责从 PDF 中提取图片和表格等非纯文本内容，并保留其对应关系。

在前面的 Layout 分析中，系统已经识别出哪些区域属于图片、表格以及对应的说明文字。Extract Table Figure 会进一步提取这些视觉元素，并保存：

- 图片内容；
- 表格内容；
- 图片/表格对应的标题和说明；
- 元素的位置关系。

核心价值：

- **完整性保证**：确保表格和图像信息完整提取，避免内容丢失；
- **跨页处理**：智能合并跨页的连续表格，保持表格结构完整；
- **标题关联**：自动匹配图片、表格与对应标题和说明；
- **结构化输出**：提供标准化的图像和表格格式，方便后续处理；
- **位置追踪**：保留原始位置信息，用于后续布局恢复和分析。


**对deepdoc优化**：跨页表格优化

如果当前页表格与下一页表格之间的坐标距离，小于一定阈值，则认为两个表格可能连续，可以进行拼接。

判断标准：

- 计算两个表格之间的位置距离；
- 与字符宽高进行比较；
- 当距离小于字符宽高的约 23 倍时，认为两个表格属于同一结构，可以合并。（经验）

##### concatdownward

Concat Downward 负责对前面解析得到的内容块进行进一步拼接，将属于同一语义区域的文本进行合并。

不断尝试将当前文本块与后续文本块进行合并，当满足拼接条件时继续向下探索；当无法继续拼接时，返回上一个节点，再尝试其他路径。

该过程类似 DFS

---
如果直接对 pdfplumber 输出的长文本进行固定长度 Chunk 切分，容易破坏原始文档结构和语义。
例如按照固定 128 token 切分时，可能将完整概念、句子甚至图表信息从中间截断，导致上下文丢失、Chunk 语义不完整。
而通过 OCR + Layout + Text Merge + Extract Table Figure 的解析流程，可以先根据文档结构识别并恢复完整文本块，同时保留图片和表格信息，再进行 Chunk 切分，使每个 Chunk 保持更完整的语义和上下文关系，提高后续 RAG 检索和生成效果。

### 数据库相关

数据库存储区别

Redis 主要用于存储临时热数据，例如临时上传文件、短期聊天上下文等，特点是读写速度极快，但内存空间有限，通常通过 TTL 机制自动释放数据
PG（PostgreSQL）是基于 SQL 的关系型数据库，用于存储与用户相关的**结构化信息**，例如 user、section、message 等表，通过 user ID、section ID、message ID 建立关联关系，用于保存用户信息、历史记录等长期业务数据
ES/向量数据库则用于**长期**存储知识库文档及其向量化数据，支持后续的全文检索和向量检索，是 RAG 知识检索阶段的核心存储。

Milvus :相比传统数据库添加了对话的内容和对应的向量
向量+元数据

#### 为什么需要向量数据库？
理论上可以直接将向量存储在 SQL 数据库中，并通过 SQL 逐个计算向量相似度进行排序。但传统数据库面对高维向量计算时效率较低，因为需要遍历大量数据并逐个计算距离，导致存储和检索效率极低。

因此引入向量数据库。向量数据库针对**高维向量检索**进行了**专门优化**，通过建立向量索引（如 ANN 近似最近邻算法），避免遍历全部数据，实现快速的相似度搜索。

速记：快速检索，高维存储，多种索引，可扩展性

#### 算法
KNN精确搜索：暴力遍历，时间复杂度O(n*d)
ANN近似搜索：跳过大部分数据 O(nlogn)

主流ANN算法：IVF，HNSW

##### IVF（倒排文件索引）

IVF（Inverted File Index）是一种用于加速向量检索的算法，核心思想是**先聚类，再缩小搜索范围**。
IVF 会先对文档向量进行聚类，将相似类型的文档放在同一个类别（Cluster）中。查询时，不再搜索全部文档，而是：

Query 输入后，先计算它与各个类别中心节点（Centroid）的相似度，找到最可能相关的类别；

然后只在该类别内部继续计算向量相似度，找到最终最匹配的文档。

##### HNSW（Hierarchical Navigable Small World）

HNSW（分层可导航小世界图）是一种用于加速向量相似度搜索的近似最近邻（ANN）算法。核心思想是**通过构建多层图结构，让查询过程快速定位到目标向量附近的区域**。

传统向量检索需要遍历大量向量计算相似度，数据规模大时效率较低。HNSW 将所有向量构建成一个图，每个向量作为节点，与其他相近向量建立连接。

#### 双塔模型（Bi-Encoder）

双塔模型将 Query 和 Document（Chunk）分别输入两个编码器：

Query
→ Embedding Model
→ Query Vector

Document
→ Embedding Model
→ Document Vector

然后计算两个向量之间的相似度（通常为余弦相似度），得到匹配分数。

#### 单塔模型（Cross-Encoder）

单塔模型会将 Query 和 Document 拼接后一起输入模型：

(Query + Document)
→ Encoder
→ Similarity Score

模型可以直接关注 Query 和 Document 之间的交互关系，因此能够更准确判断相关性。

- 精度高；
- 能理解更细粒度的语义关系；
- 计算成本高，速度慢。

2. 快速解析：从 Redis 中获取用户刚上传文件的临时解析结果（未存入 ES）。

最终将 ES 检索结果与 Redis 快速解析结果共同作为上下文输入大模型，生成最终回答。
