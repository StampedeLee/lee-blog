## 提示词工程与API的调用
### 1.定义

提示词工程是指**通过设计和优化输入给大语言模型（LLM）的提示词（Prompt）**，使模型能够稳定、准确地产生符合需求输出的过程。

### 2.参数设置
注：

**Logits** 是模型最后一层输出的、还没有经过 Softmax 转换的原始分数（raw scores）。

| 输入参数             | 参数含义 |
|----------------------|----------|
| **max_tokens**        | 指定模型可生成的最大token个数。 |
| **temperature**       | 用于控制模型回复的随机性和多样性。具体来说，temperature值控制了生成文本分布进行平滑的程度。较高的temperature值会降低概率分布的峰值，使得更多低概率词被采样，结果更加多样化；而较低的temperature值会增强概率分布的峰值，使得高概率词更容易被选择，结果更加确定。取值范围：[0,2]，不建议取值为0, 无意义。 |
| **top_p**            | 生成过程中的核采样方法概率阈值。例如，取值为0.8时，仅保留概率加起来大于0.8的最小集合作为候选集。取值范围为(0,1.0)，取值越大，生成的随机性越高；取值越小，生成的确定性越高。 |
| **top_k**            | 生成时，采样候选集的大小。例如，取值为50时，仅将单次生成中得分最高的50个候选集。取值越大，生成的随机性越高；取值越小，生成的确定性越高。默认不启用None或当top_k大于100时，表示不启用top_k策略，此时，仅有top_p策略生效。 |
| **repetition_penalty** | 用于控制模型生成时的重复度。提高repetition_penalty时可以降低模型生成的重复度。没有严格的取值范围。 |
| **seed**             | 用于生成时使用的随机数种子，用于控制模型生成内容的随机性。seed支持整数，默认为1234。 |

#### Temperature
在大模型（如Transformer架构的大语言模型）生成文本时，**temperature** 是一个超参数，用于控制**softmax** 采样的平滑程度，从而影响生成文本的多样性或确定性。

在计算下一个单词（token）的概率分布时，temperature 的公式如下：

$$
P(x_i) = \frac{\exp{(z_i / T)}}{\sum_{j} \exp{(z_j / T)}}
$$

其中：
- \( P(x_i) \) 是生成的 token \( x_i \) 的概率。
- \( z_i \) 是模型对 token \( x_i \) 的 logits（未归一化的分数）。
- \( T \) 是 temperature 超参数（通常 \( T > 0 \)）。
- 分母是所有 token 对应的指数分数的归一化项。

**因为 Softmax 中使用了指数函数 exp，所以输入值之间的小差距会被指数放大，从而形成更加明显的概率差距**

##### Temperature 的作用：
1. **高温（\( T > 1 \)）**：  
   - logits 被缩小，softmax 输出更平滑（接近均匀分布）。  
   - 增加生成文本的多样性，但也可能导致更多的无意义输出。  
   
2. **低温（\( 0 < T < 1 \)）**：  
   - logits 被放大，softmax 使高概率的 token 变得更加确定。  
   - 生成结果更加确定（更接近贪心搜索），但可能导致模式坍缩（即生成重复或单一风格的文本）。

3. **极端情况**：
   - 当 \( T \to 0 \)，softmax 近似变为 **argmax**，即只选择最高分数的 token（贪心解）。
   - 当 \( T \to \infty \)，所有 token 近似等概率，采样趋于随机。

通常，**temperature 的默认值是 1**，但可以根据任务需求调整（如 0.7-0.9 适合生成连贯但有一定创造性的文本）。

简而言之，**越高创造性越强，越低控制性越强**

>Top-p = Top probability sampling
>Top-k = Top k (Top k Sampling)

### 3. 格式化输出
结构化输出：按照固定格式来输出，⽅便后续处理，常⻅的格式有 JSON、XML

大模型 API 调用主要包含三个部分：**Client、Message 和 Response 生成配置。**

Client 负责连接模型服务，需要配置 API Key 和 Base URL；Message 负责传递用户输入和上下文信息；Response 生成时需要指定模型名称以及相关生成参数，用于控制模型最终输出。

在大模型输出控制（Structured Output）中，常见的两大方式：

JSON Schema（精细化结构约束输出）

强制 JSON 输出（控制response format）

#### 1. JSON Schema

核心思想:直接规定模型输出的数据格式。

JSON Schema 主要作用是约束和验证输出的格式与结构，方便程序解析和后续处理

如果大模型的输出不是直接给人看的，而是要作为后续程序的输入（中间数据），那么必须限制它输出固定格式，通常使用 JSON Schema。

适用于：
- 用户信息提取；
- Agent 中间参数传递；
- 数据结构化处理。

#### 2. 强制 JSON 输出（JSON Object Mode）

通过 response_format 设置模型必须输出 JSON 格式。

特点：
- 只能保证输出为 JSON（需要后处理；
- 无法精细控制每个字段；
- 存在一定格式错误概率。

需要给出Example JSON

适用于不支持 JSON Schema 的模型。

## Function_Call

Function Calling 是一种让大模型**调用外部函数或工具**的机制。

### 基本流程

**函数定义：**
预先定义可用的函数，并通过 JSON Schema 规定函数参数的结构和类型。

**函数判断：**
模型根据用户需求判断是否需要调用函数。

**函数调用：**
模型根据定义生成函数名称以及对应参数，调用指定函数。

**结果处理：**
函数执行完成后，将执行结果返回给大模型，由模型生成最终响应。

### WHY RAG？

>- **动态更新知识**：相比纯 LLM 依赖训练后的参数，RAG 可从外部知识库获取最新信息，无需重新训练模型。
>- **提高生成质量**：减少幻觉（Hallucination）问题，使生成内容更加准确和可解释。
>- **本地数据的隐私性**：企业数据一般是不能上传云端，或者进行模型训练的

还有LLM本身的局限性：**上下文的长度是有局限的**

### llama index的实现

#### 1. 什么是llama index
`LlamaIndex` 是一个用于 `LLM` 应用程序的数据框架，用于注入，结构化，并访问私有或特定领域数据。

是**目前最好**的RAG实现框架

#### 2. LlamaIndex 核心功能

LlamaIndex 是一个连接 LLM 与外部数据的框架，主要用于构建 RAG 应用。

LlamaIndex 提供 5 大核心功能：

- **Data Connectors（数据连接器）**：从数据库、API、文件系统等数据源中提取和加载数据，为后续索引和查询提供数据基础。

- **Data Indexes（数据索引）**：组织和存储已加载的数据，建立索引以提高信息检索效率。

- **Engines（引擎）**：负责驱动整个查询和生成流程。它管理用户 Query 与向量数据库之间的检索过程，将检索到的相关信息进行整合，并结合 LLM 生成最终回答。在 RAG 流程中，Engine 负责协调数据检索、上下文拼接以及答案生成等步骤。

- **Data Agents（数据代理）**：基于上下文自动执行数据处理任务，包括数据转换、合并、增强和推理。

- **Application Integrations（应用集成）**：提供与 LLM、BI 工具、SaaS 平台等外部应用的连接能力，使 LlamaIndex 能够集成到实际业务系统中。

#### 1. chunk切分（**面试实际重点**！）
在RAG系统中数据块切分的重要性

在检索增强生成（Retrieval-Augmented Generation, RAG）系统中，数据块切分（chunking）是一个至关重要的环节，直接影响系统的检索质量和生成效果。

##### 检索精度和相关性

- **语义完整性**：合理的切分能确保每个数据块包含完整的语义单元，使检索结果更加连贯有意义
- **相关性提升**：精确切分可以使检索系统更准确地匹配用户查询的真正意图，减少无关信息的干扰
- **消除噪声**：适当大小的数据块可以减少不相关内容被一同检索的可能性

##### 向量表示与相似度计算

- **向量密度**：较小的块能产生更精确的语义向量表示，使相似度计算更加准确
- **降低维度诅咒影响**：适当切分可以减轻在高维空间中相似度计算的挑战
- **检索效率**：合理大小的向量可以加速相似度计算和索引查找过程

##### 生成质量优化

- **上下文窗口管理**：适当大小的数据块能在不超过模型最大输入限制的情况下提供足够上下文
- **信息密度平衡**：切分策略影响输入到生成模型的信息密度和质量
- **减少幻觉**：精确检索到的相关块可以为生成模型提供更准确的事实依据，减少幻觉

##### 实际应用考量

- **领域特性适配**：不同领域（医疗、法律、技术文档等）可能需要不同的切分策略
- **多级切分**：有时需要采用多级切分策略，结合大块和小块的优势
- **元数据增强**：切分时保留和添加适当的元数据可以提升检索效果


##### 切分规则
基于**规则**的切分&基于**语义**的切分

**规则**一般按照：长度，结构化切分（诸如段落，章节），使用滑动窗口的切分（用重复避免语义切割）
滑动窗口切分（Sliding Window Chunking）本质上就是通过保留一部分重叠内容，避免文本被硬切断，从而保持上下文和语义连续性。（当然，不能完全避免）

**语义**一般使用余弦相似度来切分/组合段落，分为：基于主题边界的切分（两个段落大意相同），语义相似度的指导切分（根据embedding 的相似度的变化来判断）

### 3.查询引擎
查询引擎（Query Engine）用于封装整个 RAG 流程，用户只需要输入 Query，查询引擎负责完成向量检索、获取相关 Knowledge、拼接上下文并调用 LLM 生成答案。

Embedding 模型与 LLM **不存在**维度匹配问题。Embedding 模型只负责将文本转换为向量，并通过向量相似度检索 Top-K 相关文本；检索完成后，传递给 LLM 的是原始文本（Query + Knowledge），而不是向量。因此，Embedding 向量维度只影响检索过程，与 LLM 输入无关。

#### Query Transformation（查询转换）

Query Transformation 是 RAG 查询阶段优化检索效果的方法，通过对用户原始 Query 进行扩写、改写或补充上下文，生成更适合检索的 Query。

在检索过程中，Transformation 根据用户原始 Query 和 Index 中已有的知识信息，对问题进行增强，再通过向量检索获取相关 Chunk，最后将检索结果与用户问题一起输入 LLM 生成答案。

### 2. 语义分块

涉及相关代码。

关于语义切分，核心都是根据**语义相似度**，基于不同方法得到的**阈值**来进行切分。

这里同样需要系统化的评估流程。

实际关于语义切割应用不多，因为开销巨大。

语义分段虽然实际应用较少，因为需要对每个句子建立 embedding 并计算句子间相似度，面对大规模文档时计算开销较高，但它提供了一种优化文本切块的思路。

通过 Markdown 等结构化解析方式，可以利用标题、段落等逻辑关系进行更合理的分块，并进一步合并语义相关的段落，减少 chunk 数量，从而提升检索效率。


面试疑问：如何进行语义分块？

答：

语义分块根据文本语义关系切分，而非固定长度切分。

根据标点或句子边界切分文本，生成句子 embedding，计算相邻句子余弦相似度。

相似度低于阈值则判断语义变化并切分，高则合并为 chunk。

阈值可人工设定，也可根据相似度分布（如四分位数）动态确定。


### 3. 语义分块 - 切块大小

**Overlap：** 相邻 chunk 之间的重复区域，通过滑动窗口保留部分上下文，避免切分导致语义信息丢失。

构建工业系统，需要评估集（data/val.json）以及严格的评估模板。


RAG 评估主要关注两个维度：

**忠实性（Faithfulness）：**

衡量答案是否基于检索内容生成，避免出现幻觉。

**相关度（Relevance）：**

衡量检索内容和生成结果是否与用户问题相关，是否能够解决用户需求。


**幻觉（Hallucination）：**

指大模型生成了看似合理但实际不存在或错误的信息。


### 4. 上下文增强 - 上下文拼接

新增步骤：

拼接检索到 chunk 的上下文。


### 5. 上下文片段标题增强 - 文档分块

切块后为 chunk 添加标题信息，结合标题和原文进行检索，提高上下文理解能力和检索准确度。

RAG 系统中文档处理模块和在线召回问答模块相互独立。

离线文档处理不会直接影响用户响应速度，因此可以适当增加计算成本，通过更精细的处理提升效果。


### 6. 文档增强的 RAG - 用户查询

通过 **“QA 匹配 + 文档检索”** 双重机制，提高系统可靠性，降低幻觉风险。

文档增强 RAG 中通常加入意图识别模块，根据用户 query 判断问题类型。

对于企业知识库中高准确性要求的问题（如企业负责人、考勤时间等），可以提前构建 QA 数据库，通过意图识别后直接匹配标准答案，避免模型生成错误。


同时，可以利用大模型根据原始 chunk 自动生成 QA，形成问答索引。

当用户问题命中已有 QA 时直接返回答案；

未命中时，再通过传统 RAG 流程检索文档并生成回答。

### 8. 重排序 - 相似度检索之后

传统向量检索采用 **Bi-Encoder** 模式，即 query 和文档 chunk 分别经过 embedding model 转换为向量，再计算余弦相似度。


**规则重排：**

基于结构化数据的 metadata 进行重排。

例如根据文档类型、时间、来源等信息调整优先级。

当存在明确判断规则（如文本是否相关、是否能回答 query）时，规则重排简单且效果较好。


**Rerank Model：**

通常采用 **Cross Encoder**，将 query 和文档拼接后共同输入模型，直接学习二者之间的关联关系，从而更准确判断相关性并重新排序。


RAG 中通常采用两阶段检索流程。

首先使用 Bi-Encoder 对 query 和文档 chunk 分别进行 embedding，通过向量相似度快速召回候选文档（Top-K）。

然后将召回的候选文档输入 Cross Encoder，结合 query 和文档内容进行精细匹配，重新排序，选择更相关的结果用于生成回答。


**基于大模型：**

使用大模型进行 Rerank 时，通常不会直接让通用大模型生成答案，而是使用参数规模较小、速度更快的模型进行相关性判断和排序。

由于判断文本相关性（query 与文档是否匹配）比生成完整答案简单，小模型可以快速对大量候选文档进行打分，筛选出 Top-K 高相关内容，再交给能力更强的大模型生成最终回答。

Rerank 模型输出通常不是完整文本，而是文档的 index（索引）或相关性分数，减少输出量，提高处理效率。

> jieba 分词器

### 9. 相关段落提取 - 上下文组装后

在 RAG 系统中，经过检索和 Rerank 后，通常还需要进一步提取真正相关的段落，减少无关上下文，降低大模型输入压力。

属于 RAG 的**检索后处理（Post Retrieval Processing）**阶段。


### 10. 上下文压缩 - 上下文组装

当检索返回大量 chunk 时，直接将全部内容输入大模型会导致 Token 消耗增加、响应速度下降，同时大量无关信息会降低模型回答质量。

因此，可以先通过压缩模型提取上下文中的关键信息，再交给大模型生成答案。

（位于重排之后）


### 11. RAG 的反馈机制 - Final Answer 后

有些类似**缓存机制（Cache）**。

对于人工评估确认的高质量 QA，沉淀到 QA 数据库。

如果 QA 覆盖范围足够广，部分问题甚至可以完全绕过大模型，仅通过 QA 匹配完成回答。


根据**历史反馈**对文档相关性分数进行动态调整。


### 12 & 13. 自适应检索和自适应 RAG - 查询

通过意图识别对用户 Query 进行分类，根据不同问题类型选择不同的处理链路，从而针对具体场景进行优化，提高整体准确率。


常见意图类型：

- 事实型检索（Fact Retrieval）
- 分析型检索（Analytical Retrieval）
- 观点型检索（Opinion Retrieval）
- 情景型检索（Situational Retrieval）


意图识别在工业环境中存在限制：

**即使使用能力较强的大模型，通过 Prompt 优化后，意图识别准确率通常也只能达到约 80% 左右，很难稳定超过 90%。**


解决方案：

使用小模型进行微调（Fine-tuning），训练专用的意图分类模型。


> 所以项目写小模型的微调比较有效果。


**自适应 RAG 部分：**

当 Query 本身属于大模型已掌握的知识时，强行检索无关文档可能会降低回答质量。

由于 Transformer 的 Attention 会关注输入上下文中的所有 Token，无关信息可能干扰模型生成。

因此，自适应 RAG 会增加检索决策模块（Retrieval Router），判断是否需要检索：

需要 → 进入 RAG 流程；

不需要 → 直接由大模型回答。


### 14. 命题分块 - 文档分块

传统切块方式：

直接按照长度或段落切分文本，可能导致 chunk 丢失上下文信息，使单个句子无法表达完整语义。


命题分块：

将文本拆分为多个独立命题，并补充缺失的主语、背景和关键信息，使每个 chunk 都具备相对完整的语义，便于后续检索和理解。


### 15. 多模态检索融合 - Embedding

**多模态（Multimodal）：**

指模型能够同时理解、处理和关联多种类型的数据模态，例如文本、图片、音频、视频等。


针对不同多模态信息 Query，有两种方案：


1. 全转换为文本（Text-based Approach）

将图片、表格、音频等信息转换为文本，再使用传统 RAG 流程。


2. 多模态向量空间（Multimodal Embedding）

直接将不同模态信息映射到统一向量空间，通过 embedding 相似度进行检索。


### 16. 融合检索 - 相似度检索

结合：

语义检索 + 关键词检索。


### 17. 图 RAG - 相似度检索 / 上下文拼接

较为重要。

一种通过将知识组织为连接的图，而不是扁平的文档集合，来增强传统 RAG 系统的技术。


### 18. 分层检索 - 相似度检索

两级搜索方法来改进检索：

首先通过摘要识别相关的文档部分，然后从这些部分检索具体细节。


### 19. 假设文档嵌入 - 查询向量化

通过生成假设文档，将 Query 转换为更适合检索的语义表示，再进行向量匹配。


### 20. 动态纠正 - 上下文拼接

根据检索结果和生成过程动态调整上下文，提高回答准确性。


### 21. 强化学习 - 最终答案

通过强化学习优化模型最终输出，使模型根据反馈不断调整生成策略，提高回答质量。
