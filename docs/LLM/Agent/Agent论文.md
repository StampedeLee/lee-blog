## 使用 LLM 构建应用时的建议

* **从最简单的方案开始**，只有在必要时才增加复杂度。
* Agentic 系统往往会**牺牲一些延迟和成本，来换取更好的任务性能**，因此在采用之前需要评估这种权衡是否值得。
* 如果确实需要增加复杂度，可以选择**工作流（Workflow）来执行相对明确定义的任务，以获得更好的可预测性和一致性**。
* 当任务**需要大规模灵活性，以及由模型驱动决策**时，Agent 往往是更好的选择。
* 不过对于绝大多数应用来说，**通过检索或补充上下文即可实现的单次 LLM 调用，通常就已经足够。**'



>关于写简历/完善系统的建议：
>思考在场景中解决了什么问题，以及帮助谁来解决这个问题。
>找到这个领域里做得最好的人，与他交流，了解他是如何完成这个任务的。
>先用最简单最基础的方案，调用大模型接口搭建工作流
>看存在什么问题，是否有非线性，多变路径需求，看是否需要升级agent

## 什么时候（不）该使用 Agent：核心参考点
看是否涉及**灵活决策**和**多工具切换**，来判断是否使用Agent

### 任务是否高度确定、单步就能完成？

* 如果是，通常直接调用 LLM 或基于检索的简单工作流就够了。

### 是否需要多步骤 / 多工具，而且流程的顺序或逻辑并不固定？

* 如果答案是“是”，考虑使用 Agentic 系统，让模型根据上下文决定下一步。
* 如果答案是“否”，使用固定工作流即可。

### 是否能接受额外的调用成本和潜在延迟？

* Agent 往往会多次调用模型或外部工具。如果这是不可接受的，则不如使用简单的调用方式。

### 系统的可控性和可预测性有多重要？

* 工作流一般可控性更高；Agentic 系统带来灵活性的同时，也带来更高的不可预测性，因此需要更完善的监控和限制。

## 主要发现（Main Findings）

### 1. Less is More

与一些通用的 agentic 框架给模型提供大量外部工具不同，我们发现只提供两个工具（即网络搜索和编程）就足以覆盖大部分任务，即便是那些需要专家级能力的复杂任务。

**增加更多工具可能会增加模型错误使用工具的风险，也容易导致外部工具输出不准确，从而降低整体质量。**

当然，如果需要处理非文本模态的数据（例如金融数据、医学影像、基因数据等），就需要定制额外的工具，这方面会在未来的更新中继续探索。

### 2. 将任务分配给基于 LLM 的代理

**将计算工作分配给多个基于 LLM 的代理能提高效率。**

与让主推理模型自己写代码或直接调用非 LLM 工具（如纯搜索引擎或代码编译器）相比，我们让专门的 LLM 代理来做对应的子任务（例如让某个编码 LLM 来生成并执行代码，或者让构图 LLM 将推理链转化为知识图）。

这有两个明显好处：

* **减少主推理的中断：** 主模型可以保持更长、更连贯的推理，不被各种辅助任务打断或占用过多 token；
* **利用不同 LLM 的特长：** 不同 LLM 在不同任务上的表现更佳，例如 DeepSeek-R1 专注于逻辑推理，而 Claude-Sonnet 在编程上更擅长。将任务分配给最擅长的模型可以在整体上获得更优表现。

### 3. Agentic Test-time Scaling?

我们观察到，对同一个问题来说，**如果推理链使用了更多的工具调用，往往可以得到更好的解答；** 但若某些问题需要过于频繁、密集的工具调用，往往说明最初的推理就存在一定的歧义或不准确。

这个现象可以用来做推理结果的验证：我们可以通过挑选工具使用频率最高的推理链来做 best-of-N 的选择，或者结合集束搜索（beam search），从而在需要多个步骤来检验正确性时（例如数学或编程任务）**提升结果的准确率和鲁棒性。**

这一方法同样可以拓展到开放域（open-domain）和知识密集型问答中，用类似的思路进行结果筛选和验证。
