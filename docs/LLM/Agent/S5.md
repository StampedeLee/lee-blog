# AI Skills 与 Agent 上下文工程

## Skills 框架思考

Skills 的核心价值是增强 Agent 的**决策力**：把特定领域的 Know-how、执行规则和可复用资产组织起来，让 Agent 知道什么时候使用、如何使用。

一个完整的 Skill 通常由以下内容组成：

| 组成部分 | 作用 |
| --- | --- |
| `SKILL.md` | 描述 Skill 的适用场景、触发条件和使用方法 |
| Metadata | 提供名称、描述等检索与匹配信息 |
| Body | 承载核心流程与行为约束 |
| `references/` | 存放按需读取的参考资料 |
| `assets/` | 存放品牌素材、模板等资产 |
| `scripts/` | 存放可重复执行的脚本 |

一个文件夹就可以构成一个 Skill，`SKILL.md` 再按需指向 `references/`、`assets/` 和 `scripts/` 中的资源。

## 为什么需要 Skills

直接使用 MCP 或大量工具时，容易遇到以下问题：

- 工具定义过多，造成上下文膨胀。
- 模型并不需要每个工具，却必须在大量描述中做选择。
- 工具选择依赖模型猜测；当候选工具增多时，调用准确率可能下降。
- SFT 模型通常在工具数量较少、边界清晰的场景下表现更稳定。
- Multi-Agent 架构虽然能拆分任务，但搭建和维护成本较高。

Skills 通过**渐进式披露**控制上下文，把业务 Know-how 集成到 Agent 中，只在需要时加载对应知识与规则。

### 渐进式披露流程

```text
System Prompt
    ↓
匹配 Skill
    ↓
读取 SKILL.md
    ↓
按需加载 Reference / Asset / Script
    ↓
调用工具
    ↓
输出结果
```

如果需要触发某个 Skill，还要确保运行环境与 Skill 声明的容器或依赖要求兼容。

## Skills 的四级实践

1. **最简版**：只有 `SKILL.md`，包含触发条件和执行步骤。
2. **平台规范**：补充元数据、目录结构和输入输出约束。
3. **品牌资产**：加入模板、视觉资产和领域参考资料。
4. **完全体**：增加脚本和自动化校验，使经验可以稳定执行。

## 案例：Python 工具的状态丢失

### 核心问题

Agent 在多步任务中多次调用 Python。由于底层执行环境是无状态的独立进程，前一次调用中的变量不会保留，后续代码容易出现 `NameError` 等错误。

### 规则设计

强制每次执行都包含完整的 `import`、变量定义和必要的前置数据。

### 解决方案

1. 尽量把多步操作合并为一个完整脚本。
2. 必须拆分时，通过 CSV、JSON、PNG 等文件传递中间结果。
3. 不允许假设上一次调用中的变量仍然存在。

## 面试故事：解决 Agent 的“记忆丢失”问题

### Situation：背景

在一个数据分析 Agent 项目中，用户可以通过自然语言要求模型执行 Python 代码，完成数据清洗和可视化。

### Task：挑战

测试阶段发现，当用户提出“读取 CSV、清洗数据、生成柱状图并导出 PDF”一类多步任务时，Agent 会把任务拆成多次 `execute_python` 调用。

模型习惯性地认为之前定义的变量仍然存在，例如在后续调用中直接执行 `df.plot()`。但底层沙箱每次都会启动新的独立进程，进程之间不会共享内存和变量，因此第二步或第三步经常执行失败。

### Action：行动

我从行为约束和执行环境两个维度处理这个问题：

1. **完善 Skill 与 Prompt 规则**：明确说明每次调用都是独立进程，要求每段代码包含完整的导入和前置数据定义。
2. **设计数据持久化机制**：多次调用之间使用 `temp.csv`、`intermediate.json` 等文件传递中间结果。
3. **合并执行逻辑**：尽量把数据处理、绘图和 PDF 导出合并到一次 Python 调用中完成。

### Result：结果与反思

调整后，Agent 的执行失败率明显下降，代码兜底能力得到提升。

这个问题说明，大模型应用开发不仅是编写 Prompt，也是系统工程设计。模型不了解底层进程的物理状态，开发者需要通过规则约束、文件持久化和自包含脚本，弥补执行环境的状态缺失，让 Agent 从原型走向可用的生产工具。

## `execute_python` 使用规则

> **重要：每次 `execute_python` 调用都是独立进程，多次调用之间不会共享变量。**

因此必须遵守以下规则：

1. 每次调用都包含完整的 `import` 和数据定义。
2. 多步操作应尽量写在同一次调用中。
3. 需要拆分时，通过 CSV、JSON、PNG 等文件传递数据。
4. 不要假设上一次调用中的变量仍然存在。

## 双层按需加载机制

### 策略层：加载 Skill

Skill 提供知识、规则和宏观流程，解决“**怎么做**”的问题。

策略层通过渐进式披露做加法：不一次性把所有信息交给模型，而是按需将 Skill 的规则和工具执行结果逐步追加到消息列表中。

### 执行层：调用 Tool

Tool 提供 CRUD 能力和执行环境，解决“**用什么做**”的问题。

Agent 不会一次性加载全部工具参数。只有决定执行具体动作时，才读取对应工具定义，从而减少无关上下文和 Token 消耗。

### 载体层：显性化上下文

Agent 的思考、动作和观察都会转化为文本：

```text
Thought → Action → Observation
```

这些内容持续追加到 Message List 中。不断增长的消息列表，就是模型可见的“记忆账本”。

## 总结

- Skills 负责沉淀策略、规则和领域经验。
- Tools 负责执行具体操作。
- 渐进式披露负责控制上下文规模。
- Message List 负责承载模型可见的过程状态。
- 文件持久化负责解决无状态工具之间的数据传递问题。
